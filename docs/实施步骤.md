## 0. 推进策略

1. **先纵向切片，再横向铺开。** 第一条必须打通的链路是：
   `demo APK → S1 清点 → S2 容器 → stub 启动 → 内存加载 DEX → 原 Application 正常运行`。
   后续每个能力都必须挂在这条链上验证，禁止先铺一堆孤立模块。
2. **格式草案先行，原型后冻结。** 容器 v2、签名清单、C ABI 先出中立规格与跨语言测试向量，Python 与 C++ 各自实现并交叉验证；P0 先做最小双端编解码实验，P1 联调后冻结发布格式；密码依赖在实验前选定。
3. **四个 M0 原型并行**（§16.7）：容器与授权、透明接管与恢复、完整 DEX 加载、透明 SharedPreferences/普通文件。原型未过，不进入 M1。
4. **公开 API 优先。** 基线用 `InMemoryDexClassLoader` + 完整 DEX 缓冲；ART 内部适配只在有真实失败证据时引入，默认不改全局 `VerifyClass`。
5. **在线档先行。** M1 主线是 `online_authorized`；`offline_compatible` 后置，且不用于宣称 G2 达标。
6. **Definition of Done**：代码 + 单元/格式测试 + 中立规格 + 证据记录（设备、版本、样本、时间）+ 依赖 ADR（如引入 OSS）+ 更新功能矩阵状态。缺一项不算完成。

## 2. 目标工程结构

在现有骨架上演进，不推翻重来：

```text
frontend/src/                 # Vue/TypeScript
backend/
  cmd/                        # Go API
  internal/                   # 单体业务、授权、事件、任务
  pipeline/                   # Python worker、CLI、Java DEX 工具及脚本
  migrations/                 # PostgreSQL
  tests/                      # 测试与格式向量
android/
  app/                        # Studio 宿主
  shield/                     # 待建 Java/C++ library
docs/                         # 设计、研究、格式和 ADR
```

**模块边界决定：**

- `:shield` 同时产出 Java stub 与 `libshield_boot.so` / `libshield_core.so`；生产形态由流水线拆包注入，开发期由 `:app` 直接依赖，二者 manifest 改法必须一致。
- Python 流水线只消费已构建的 `:shield` AAR/so，不直接编译 Java/C++。
- P1 建 Go 单体 API、Python worker 和开发授权；P2 完善生产授权和 Web 闭环。

## 4. P0：基线与契约冻结（2 周）

### P0-01 版本控制与基线

- 确认版本控制位置（本目录 `git init` 或纳入现有仓库），提交当前骨架为基线。
- 建立分支约定：`main` 可发布、`proto/*` 原型、`fmt/*` 格式冻结。
- 产出：基线提交、`docs/开发环境.md` 更新。

### P0-02 工具链固定

- 固定并记录：JDK（与 AGP 9.5.1 匹配）、NDK（r27+）、CMake 3.22.1、Python 3.11+、adb、`apksigner`/`zipalign`、后续 Go 1.22+。
- 记录完整版本、安装路径、SHA-256；NDK 需同时支持 arm64-v8a 与 16 KB 页检查。
- 产出：`docs/开发环境.md` 工具链表；`backend/pipeline/scripts/check-env.sh`。

### P0-03 Gradle 多模块与构建骨架

- 新增 `:shield`（Java + CMake），`app` 改为依赖它；保留模板代码作为 harness 起点。
- 配置两个 native target：`shield_boot`（≤ 50 KB 目标）、`shield_core`；`-std=c++17`、隐藏内部符号、`-Wl,-z,relro,-z,now` 作为基线开关（是否启用按 NDK 验证）。
- 增加 keep 规则：stub 类、恢复组件不可被 R8 删除。
- 产出：可 `assembleDebug` 的多模块工程；APK 内含两个 so。

### P0-04 C ABI v1

- 按 §10.1 落地 `abi.h` / `boot.h` / `core.h`：`extern "C"`、固定宽度类型、不透明句柄、显式所有权、统一错误码。
- 所有结构体带 `struct_size` 与 `abi_version`；禁止跨边界传 STL/异常/RTTI。
- 写一个 C 编译单元仅包含头文件，确保可被非 C++ 调用方使用。
- 产出：头文件、ABI 说明、编译测试。

### P0-05 容器 v2 规格冻结（关键路径）

- 写 `docs/formats/container-v2.md`，必须明确：整数端序、字段宽度、长度上限、区域偏移、TOC 布局、签名覆盖范围、未知标志处理。
- 密码契约按 §16.3：每构建 256 位 `K_content`；HKDF-SHA-256 按 `build_id` + 用途标签派生块/TOC 密钥；块 nonce = 8 字节随机前缀 + 4 字节大端全局块号；AAD 固定编码绑定格式、算法、`build_id`、文件序号、块号、明文长度。
- 明确 `file_id` 只作标识，不承担 nonce 唯一性。
- 产出：规格文档 + `backend/tests/vectors/container/` 正例与负例（重排、截断、错误 tag、重复 nonce、超大长度）。

### P0-06 清单与策略格式 v1

- `manifest.sig` JSON schema：产物列表、哈希、版本三元组、`cert_sha256`、Ed25519 签名；明确规范化方式与签名覆盖字段，避免自哈希循环。
- `policy.pkg`（SPK1）字段按 §4.S3；`rules.pkr`（PKR1）已实现头部与 JSON 载荷，含可选 `yidun` 段，见 `docs/formats/rules-v1.md`。
- 产出：`docs/formats/manifest-v1.md`、`policy-v1.md`、示例包与解析测试。

### P0-07 Harness 应用

- 在 `:app` 中补齐：自定义 `Application`、自定义 `ContentProvider`、Activity、Service、Receiver、第二进程、SharedPreferences、普通文件、SQLite。
- 构建变体：debug / release；release 开启 R8，验证 keep 规则。
- 产出：可安装 APK；组件清单与预期启动时序记录，作为接管验收基线。

### P0-08 功能说明与依赖流程

- 落地模板：`docs/specs/<功能编号>.md`（输入输出、状态机、异常、证据级别），按需补充来源和对照测试。
- 明确九条规则等逆向产物只作研究证据，产品规则另行独立编写并记录特征来源（§17.6、实现原则 §3）。
- `components.lock.json` 增加 registry 字段；任何 OSS 引入先出 ADR，GPL/AGPL 禁止进入客户端。
- 产出：模板与首个 ADR（容器密码库在 P0 最小编解码实验前完成选型及许可审核）。

### P0-09 本地检查脚本

- `backend/pipeline/scripts/check.sh`：构建 `:shield` 与 `:app`、跑单元测试、跑向量交叉验证、检查 so 符号与对齐。
- P2 再替换为 CI；先保证任何人在本地一条命令复现。

**G0 退出条件**：容器/清单规格签字；Python 与 C++ 对同一组向量结果一致；harness 可安装并跑通全部组件；工具链版本与哈希入库。

**P1 补充进展（2026-11-21）**

## 6. P2：M1 最小闭环（6–8 周）

目标：一条可对外演示、可红队验收的完整链路。

1. **密钥与授权**
   - `授权模块` MVP：设备注册（Keystore 公钥）、构建/证书/挑战校验、内容密钥封装、短期授权缓存、吊销接口。
   - Core 密钥提供者：在线取钥、Keystore 解包、内存中只保留必要生命周期。
   - 断网/吊销/首装失败的降级路径与原因码。
2. **构建流水线补齐**
   - S3 策略包、S5 客户 so 符号裁剪与 ABI 校验、S6 完整注入、S7 `zipalign -P 16` + 签名模式（HSM / 客户本地）、S8 `gate.json`。
   - `build.meta` 作为唯一真相，S8 全量校验。
3. **完整性与防降级**
   - 清单 Ed25519 验签、启动关键产物全量校验、运行时抽样（8–16 段）、证书摘要绑定、版本三元组服务端拒绝。
4. **恢复与回滚**
   - 首装失败、缓存损坏、密钥不可用、版本不匹配四类恢复路径；stub 独立可用。
5. **红队闸门**
   - 复用 `analysis/tools` 思路写同构器：自解密重放、容器静态还原、文件还原、清单伪造、规则伪造。
   - 接入 S8：按配置、资产、攻击者能力执行必选闸门；攻击成功阻断，工具报错/超时为 inconclusive。Core 可分析不自动等于业务 DEX 可恢复，规则等未实现项在 P3 纳入。

**G2 退出条件**：Web 上传→任务→加固→验证→下载和访问控制通过，CI 接入供应链检查；A1/A2/A5/A6 按在线档威胁模型通过；harness + 一个真实内部应用端到端加固成功；红队报告与残余风险记录。

## 7. P3：M2 文件、规则与事件（6–8 周）

1. **文件保护扩展**：随机访问、`mmap/msync/munmap`、`truncate`、`rename`、文件锁、跨进程、动态库载入；SQLite/WAL 未通过一致性验证前明确排除；FILE-06 历史格式迁移工具。
2. **规则引擎**：从源码构建 YARA（固定版本）；研究侧九规则受控对照，产品规则独立编写并记录来源许可与正反例、`PKR1` 加密+签名、版本门控、热更新与原子替换。
3. **事件与上报**：结构化事件、类别过滤、本地加密队列（去重/限额/重试）、批量上报、断网与磁盘满行为。
4. **服务端**：`事件模块` 接入与存储；事件与响应策略分离。

**G3 退出条件**：A3/A4 通过；九条规则语义测试与缺一特征用例通过；队列故障注入通过。

## 9. 跨阶段工作流

| 工作流 | 频率 | 要求 |
|---|---|---|
| 实现与验证 | 每个功能 | 参考研究结果独立实现，通过功能说明和对照测试验收；研究与开发可在同一人员/工具/会话中完成 |
| 供应链 | 每次引入/升级 | ADR + 完整 commit + 校验和 + 许可证 + NOTICE + owner；GPL/AGPL 禁入客户端 |
| 格式 | 每次变更 | 规格 + 正负向量 + Python/C++ 交叉验证 + 版本号；禁止静默改布局 |
| 测试 | 每包 | 单元、格式、负例、设备、故障注入；工具异常不算防护通过 |
| 性能 | 每阶段 | 同设备、同包、同场景对比；报告样本量与分位数 |
| 证据 | 每验收 | 功能编号、构建 ID、设备、ART/ABI、样本哈希、结论与限制 |

## 11. 前置决策与风险

| # | 决策/风险 | 影响 | 处理 |
|---|---|---|---|
| D1 | 首装必须联网，业务是否接受 | 高 | P0 内与业务确认；不接受则提前评估 `offline_compatible` 的信任降级 |

| D8 | GPL 禁令与工具选型 | 中 | 客户端依赖逐项审；研究/内部工具隔离，不共享代码 |
