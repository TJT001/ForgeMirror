# 2026-11-21 P2：16 KB 页适配

## 范围

让加固产物的 native 段、APK 内 `.so` 对齐和自研 ELF loader 适配 16 KB 页设备：
ELF `PT_LOAD` 对齐到 16 KB、APK 内未压缩 `.so` 按 16 KB 对齐、S8 gate 校验，
并对业务 so 的 4 KB 对齐给出警告。

## 实现

| 位置 | 内容 |
|---|---|
| `android/shield/src/main/cpp/CMakeLists.txt` | 全 target `-Wl,-z,max-page-size=16384`；arm64/arm32/x86_64 产物均为 `p_align=0x4000` |
| `formats/axml` / 构建链 | 无硬编码 4 KB；`tools.align_apk` 已使用 `zipalign -P 16` |
| `apk.elf_max_page_size` | 解析 ELF32/64 `PT_LOAD` 最大 `p_align` |
| `protect.py` | 对 base/split 中 64 位业务 so 检查；`p_align < 0x4000` 产生 `W_16KB_ALIGN` |
| `tools.verify_page_alignment` | `zipalign -c -P 16 -v 4` 校验 APK 的 `.so` 页对齐 |
| `cli._attach_page_checks` | gate 对 base 及每个 split 追加 `page_alignment_16k:<file>` 检查，失败即 S8 失败 |
| `elf_loader.cpp` | 页大小来自 `sysconf(_SC_PAGESIZE)`；`mmap/mprotect/RELRO/segment` 均按运行时页大小对齐 |

## 验证

### 构建与产物

```text
libshield_boot.so (arm64-v8a)  LOAD ... R E 0x4000
libshield_boot.so (armeabi-v7a) LOAD ... R E 0x4000
libshield_boot.so (x86_64)      LOAD ... R E 0x4000

zipalign -c -P 16 -v 4 protected.apk
Verification successful
```

`gate.json`：

```json
{"name": "page_alignment_16k:protected.apk", "status": "pass"}
```

保护后的 base/split 均纳入同一检查；split 集合逐文件检查。AAB split 输出同样覆盖：
`protected.apk`、`base-arm64_v8a.apk`、`base-en.apk`、`base-xxhdpi.apk` 均为
`page_alignment_16k=pass`。

### 自研 loader 的 16 KB 主机级验证

宿主机为 macOS arm64（`getconf PAGE_SIZE = 16384`），用 NDK 生成无依赖的
AArch64 Android ET_DYN 测试库（`p_align=0x4000`，含 RELATIVE relocation 和
`DT_INIT_ARRAY` constructor），把 `elf_loader.cpp` 用 stub `elf.h/android/log.h`
编译到宿主机执行：

```text
[FMElf] loaded libtest.so base=0x1047b0000 size=65536
value=42 ctor=7 inside=1 page=16384
```

覆盖 16 KB 页下的 `mmap`、segment 保护、RELATIVE relocation、INIT_ARRAY、
符号解析和地址归属判断。

### x86_64

构建产物：x86_64 的 `libshield_boot/yara/dummy/core/hook` 均为 `p_align=0x4000`。
x86_64 native hook 使用 Dobby（LSPosed fork，Apache-2.0，静态链接进
`libshield_hook`）；arm/arm64 继续使用 ShadowHook。Java 层
`ShieldNativeFileHook` 在库缺失的 ABI 上返回 `-2` 并继续启动。

x86_64-only APK 保护后 S8：

```text
page_alignment_16k:protected.apk  pass
zipalign -c -P 16 -v 4 protected.apk
Verification successful
```

x86_64 AAB split 集合（base + x86_64/en/xxhdpi）同样全部 `page_alignment_16k=pass`。

loader 主机级验证（x86_64 进程经 Rosetta 运行，编译期把页大小固定为 16384，
并用 16 KB 对齐的 `mmap` 包装模拟 16 KB 内核）：

```text
[FMElf] loaded libtest_x64.so base=0x108d18000 size=65536
value=42 ctor=7 inside=1 page=4096
```

即 x86_64 的 RELATIVE relocation、INIT_ARRAY、符号解析和代码执行正常；打印的
`page=4096` 是宿主实际页大小，loader 使用测试 override 的 16384 对齐。

### Android 16 KB 真机矩阵

API 37 arm64 `google_apis_ps16k` 镜像：

```text
$ adb shell getconf PAGE_SIZE
16384

ShieldRuntime: bootstrap ok state=4
FMElf: loaded libdemo2.so base=... size=32768
FMElf: loaded libdemo.so base=... size=442368
MainActivity: probe ... dependency=7 dlopen=7 lockErr=0 overload=11/12
```

同一 16 KB 镜像上 `install-multiple` 安装 AAB split 集合
（base + arm64/en/xxhdpi）后探针同样全通过；ShadowHook、dlopen 重定向、
透明 I/O 均正常。v2rayNG 2.4.0 回归 `bootstrap ok state=4`，MMKV 报告
`page size 16384` 并正常加载。

### 4 KB 业务 so

对 `p_align=0x1000` 的 64 位业务 so，protect 元数据产生：

```text
W_16KB_ALIGN: lib/arm64-v8a/<name>.so max-page-size=0x1000
```

自研 loader 使用匿名映射，不依赖平台 linker 的 `p_align`；平台 fallback 在 16 KB
设备上是否成功取决于原始 so，因此保留警告而不静默通过。

## 限制

1. API 37 arm64 ps16k 镜像已验证单 APK 与 AAB split；Apple Silicon 的 SDK
   emulator 只有 aarch64/armel qemu，x86_64 Android 16 KB 镜像运行时未验证，
   仅完成构建、APK/AAB gate 和 x86_64 loader 的 16 KB 对齐模拟。厂商 ROM 亦未覆盖。
2. 业务 so 的 4 KB 对齐只能告警，不能在保护阶段安全重排程序头；需要客户重新链接。
3. 32 位 ABI 在 16 KB 页设备上没有 32 位运行时，产物仍保留但不在该矩阵内。
4. x86_64 使用 Dobby 后端；arm64 临时 Dobby 冒烟出现 scanner 线程
   `SIGSEGV`，因此生产 arm/arm64 仍使用 ShadowHook，不启用 Dobby。x86_64
   无 Android 运行镜像，Dobby 运行时行为未在设备上验证；x86_64 产物通过
   编译、APK/AAB 16 KB 对齐和 S8 gate。
5. `--no-strip` 可能保留压缩的客户 so，`zipalign -P 16` 校验会失败；默认 strip
   路径会把客户 so 重写为未压缩条目。
