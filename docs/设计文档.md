## 1. 背景与目标

### 1.1 参照对象的形态（已核实）

- **交付形态**：后端/云端整包加固（repack），非开发期 SDK。证据：manifest 三处改写（`application=com.secneo.apkwrapper.AW`、`appComponentFactory=...AP`、注入 `provider ...CP`）；APK `classes.dex` 为 **134,024,136 B 明文多 DEX 容器**（7 处 `dex\n`、熵 6.37），运行时容器 `classes.jar`（同尺寸/同头）由壳 mmap 后在内存原地解密（§24、§28）；`assets/coreclasses.bangcle`、`assets/info.y`、`assets/meta-data/{manifest.mf,rsa.pub,rsa.sig}` 均为打包期产物。
- **运行时结构**：Bootstrapper（明文尾段 + 直接 syscall）→ 自解密首段 → `JNI_OnLoad` → DEX 内存加载 → 检测线程。
- **安全强度（分析结论）**：属于"隐藏式保护 + 可绕过检测"，不构成白盒密码。静态可完整还原：`unpack.py` / `fdex_unpack.py` / `dve_rc4.py` 分别覆盖自解密、DEX 解密、文件加密，均无需设备（§16–§19、§39、§43–§44）。

### 1.2 本设计目标

| # | 目标 | 可验证口径 |
|---|---|---|
| G1 | 能力不低于参照对象（透明加载、DEX 保护、文件策略、规则检测、完整性） | 功能矩阵对照（附录 A） |
| G2 | 无在线依赖、无 root 设备时不可完成静态还原 | 红队回归矩阵全部失败（第 13 章） |
| G3 | 攻击可被服务端感知并止损 | 吊销/降级链路可演练 |
| G4 | 启动与稳定性可控 | 启动增量 < 150 ms，崩溃率增量 < 0.05% |
| G5 | 可维护：换版本不重写工具链 | 指纹 + 分层替换（第 11 章） |

### 1.3 明确不做的事

- 不追求"不可破解"。客户端明文的 DEX/so 最终可被内存 dump（§21、§22 已实证），本设计只抬高成本并缩短明文窗口。
- 不在客户端做不可逆自毁（`kill(SIGKILL)`，§61）。
- 允许隔离的 ART 适配层，按版本与 ABI 验证；不默认修改全局 VerifyClass（详见 §16.1）。

## 3. 总体架构

### 3.1 部署视图

```
┌──────────────── 构建集群（离线/内网） ────────────────┐
│  S0 准入 → S1 清点 → S2 DEX → S3 策略 → S4 规则       │
│  → S5 原生库 → S6 壳注入 → S7 重打包签名 → S8 自检    │
│                     │                                  │
│                     └── HSM：K_app、Ed25519 签名私钥    │
└─────────────────────┬──────────────────────────────────┘
                      │ 加固 APK（未签名或客户本地签名）
                      ▼
┌──────────────── 运行期 ────────────────────────────────┐
│  Java 层：CP → AP → AW（stub DEX，约数百类）            │
│  Native：Bootstrapper → Core                           │
│  外部依赖：密钥服务（首次/轮换）、风控上报、规则下发     │
└────────────────────────────────────────────────────────┘
```

### 3.2 组件视图

| 组件 | 形态 | 职责 | 是否含密钥 |
|---|---|---|---|
| Stub DEX | Java 类 | 组件代理、最早执行点、加载触发 | 否 |
| Bootstrapper | 小 so（≤ 50 KB） | 申请 K_content、校验 Core、装载 Core | 否（仅公钥） |
| Core | so（每 App 重新构建） | 解密、DEX 装载、完整性、检测、上报 | 运行时持有 |
| 策略包 | 加密+签名数据 | 文件加密规则 | 否 |
| 规则包 | 加密+签名数据 | 检测规则（编译后） | 否 |
| 签名清单 | 数据 | 全产物哈希 + 版本 | 否（仅公钥） |

### 3.3 设计原则

1. **构建期做一次性重活**，运行时只做必须现场做的事。
2. **确定性优先**：能在离线重放的逻辑不进运行时（对照 §11.1 把 maps 自检塞进 `DT_INIT` 的反例）。
3. **密钥不在客户端可推导**：任何"静态常量 ⊕ 公开信息"的派生都禁止。
4. **响应可逆、止损在服务端**。
5. **每层可独立替换**，靠 fingerprint 判定复用边界。
6. **独立实现与行为等价**：参考逆向结论、接口、格式和实验结果自主编写代码，追求功能与行为等价；研究与开发可由同一人员、工具及会话完成。不复制未经授权的原厂代码或资产，开源复用按许可执行，以必要的功能说明和对照测试验收。见项目 docs/实现原则.md。

## 4. 构建期流水线（S0–S8）

### 4.0 总契约

```json
// build.meta（流水线唯一真相，S7 写入，S8 校验）
{
  "build_id": "uuid",
  "app": {"package": "com.x", "version_code": 1, "cert_sha256": "..."},
  "profile": "basic|enhanced|financial",
  "shell": {"version": "1.0.0", "salt": "hex"},
  "artifacts": [{"path": "...", "size": 0, "sha256": "..."}],
  "hashes": {"inventory": "sha256", "container": "sha256", "policy": "sha256", "rules": "sha256"},
  "signature": "ed25519:base64"
}
```

### S0 准入

**输入**：`{apk, signing_mode, cert_allowlist, build_id, profile}`
**输出**：`intake.json`
**校验**：APK 可解析；证书 SHA-256 在白名单；未检测到已加固标记（`com.secneo.*`、`dexdata0`、`*.bangcle`）；`min_sdk ≥ 26`。
**失败**：拒绝并返回原因码，不进入后续 stage。
**约束**：客户 keystore 不进入平台（`signing_mode=customer_local` 时只输出对齐后的未签名包）。

### S1 清点

**输入**：APK
**输出**：`inventory.json`

```json
{
  "package": "com.x", "version_code": 1, "min_sdk": 26, "target_sdk": 34,
  "abis": ["arm64-v8a"],
  "dex": [{"name": "classes.dex", "size": 0, "sha256": "..."}],
  "libs": [{"path": "lib/arm64-v8a/libx.so", "size": 0, "sha256": "..."}],
  "assets": [{"path": "assets/x", "size": 0, "sha256": "..."}],
  "components": {"application": "...", "providers": [], "activities": 0},
  "anomalies": [{"kind": "abi_mismatch", "detail": "x86 so in arm64 dir"}]
}
```

**要点**：
- 记录 ABI 目录与 so 实际架构是否一致（对照 §62.1 的错放）。
- 生成 `fingerprint`：`{package, version_code, shell_version, policy_version, rule_version}`，用于"是否需要重新加固"。

### S2 DEX 处理

**输入**：`inventory.dex` + `profile`
**输出**：`container.fdx`、`dex_manifest.json`

处理步骤：
1. 可选 multidex 合并（D8/R8 或自研 merger；保留 debug info 策略按 profile）。
2. 每个 DEX 计算 `file_id = LE64(sha256(orig)[0:8])`。
3. 分块 AEAD：`chunk = 64 KiB`，`nonce = random_prefix(8) || global_chunk_idx(4)，具体见 §16.3`。
4. TOC 单独加密（key = `HKDF(K_content, "toc")`）。
5. 组装容器 v2（格式见 7.1）。
6. **流水线内自测**：解密回读必须与原 DEX 逐字节一致，否则构建失败。

**禁止**（对照项）：只加密前 128 KB（§39.6）；明文 TOC（§39.6）；ECB（§39.3）。

### S3 策略包

**输入**：`inventory` + 客户规则（可选）
**输出**：`policy.pkg`（加密 + 签名）

```json
{
  "version": 3,
  "enc_type": "aead",
  "rules": [{"pattern": "shared_prefs/*.xml", "action": "encrypt"}],
  "excludes": [{"pattern": "databases/*.db"}],
  "min_shell_version": "1.0.0"
}
```

**要点**：策略不落明文文件（对照 §42 的 `.edata` 可读可改）；运行时由 Core 解析。

### S4 规则包

**输入**：规则源（YARA）
**输出**：`rules.pkr`

```
magic "PKR1" | version | min_shell_version | cipher | payload | ed25519_sig
```

**要点**：
- 编译后加密（`HKDF(K_content,"rules")`），签名覆盖 `version + min_shell_version + payload`。
- 校验使用签名而非裸哈希（对照 §50 的 MD5 可离线重算）。
- 规则更新走签名校验后覆盖，且带版本门控（对照 §49 的 `H.sn` 只校验 MD5）。

### S5 原生库

**输入**：`inventory.libs`
**输出**：处理后的 `libs/`

| 对象 | 处理 |
|---|---|
| 客户 so | 仅做符号裁剪、可选字符串加密；**不重写客户代码** |
| Shield so（Bootstrapper/Core） | **每 App 重新构建**，注入 `app_id`、`build_salt`、验证公钥和构建配置（在线档不嵌入主密钥） |
| ABI 目录 | 严格按实际架构放置；x86 仅用于模拟器场景且显式标注 |

**要点**：一版壳通杀所有 App 等于把壳当公共攻击面；加盐隔离配置，但共性漏洞仍需修复和回归。

### S6 壳注入

**输入**：S2–S5 产物 + manifest
**输出**：改写后的 APK 内容树

| 动作 | 要求 |
|---|---|
| `application` | 改为 Shield 的 Application 代理 |
| `appComponentFactory` | 改为 Shield 的工厂类 |
| 注入 provider | 用于最早执行点（密钥预取） |
| stub DEX | 注入，含代理类与加载触发 |
| assets | `policy.pkg`、`rules.pkr`、`manifest.sig` |
| 冲突检测 | 原包已有 `appComponentFactory` 时需合并而非覆盖 |

### S7 重打包与签名

**输出**：加固 APK + `build.meta`

- `zipalign -P 16`（Android 15 起 16 KB 页对齐）。
- 签名：`signing_mode=hsm` 时 HSM 内完成；`customer_local` 输出对齐包，由客户签名。
- 不做任何"二次签名/签名替换"。

### S8 自检与红队回归

**输出**：`gate.json`

| 攻击项 | 工具 | 通过条件 |
|---|---|---|
| 自解密重放 | 自研 `unpack` 同构器 | 无在线依赖时**失败** |
| DEX 静态还原 | `fdex_unpack` 同构器 | 无密钥时**失败** |
| 文件加密还原 | `dve` 同构器 | 无设备密钥时**失败** |
| 规则解析/伪造 | `yara_dump` 同构器 | 无法解析、无法生成合法包 |
| 完整性伪造 | 签名校验器 | 任何篡改被拒 |

**任何一项在离线条件下通过 → 阻断发布**。这是流水线的质量闸，也是 `analysis/tools/*` 的直接复用点。

## 5. 运行时壳

### 5.1 Java 层

| 类 | 对应参照 | 职责 |
|---|---|---|
| `ShieldProvider` | `com.secneo.apkwrapper.CP` | Application 附加后执行，启动后台校验；提前加载由工厂或 attach 入口完成 |
| `ShieldAppComponentFactory` | `...AP` | 接管 Activity/Service/Receiver/Provider 实例化 |
| `ShieldApplication` | `...AW` | 代理真实 Application，`attachBaseContext` 中加载 Bootstrapper |

**约束**：所有代理类不承载业务逻辑，且必须可被 R8 保留（keep 规则随包提供）。

### 5.2 启动时序与 5.3 加载策略

采用第 16.1 节的透明接管状态机和双路线架构；该节完整替代原有 provider 提前取钥与纯公开 API 假设。

### 5.4 内存策略

- 解密到**匿名页**，不使用 file-backed 可写映射（对照 §25.2 的原地解密）。
- DEX 页 `PROT_READ`；解密缓冲区用后 `memset_s` 并 `mprotect(PROT_NONE)`（尽力而为，明确记录残余风险）。
- 不追求"防 dump"，只缩短明文窗口。

## 8. 完整性与防降级

| 层 | 对象 | 机制 |
|---|---|---|
| 构建期 | 所有产物 | 哈希写入签名清单（私钥在 HSM） |
| 运行期-启动 | 清单签名 | Ed25519 校验（公钥内置 Core） |
| 运行期-运行时 | Core 自身、关键 so 段、策略/规则包 | **抽样校验**（每次启动随机抽 8–16 段），避免全量开销 |
| 运行期-环境 | APK 证书摘要 | 与 `cert_sha256` 绑定，防重签名替换 |
| 防降级 | 版本三元组 | 服务端拒绝旧 `shell/policy/rule` 版本 |
| 禁止 | 裸哈希、返回地址字面量 | 可离线重算（对照 §50、§11.1） |

## 9. 检测与响应

### 9.1 检测面

| 类别 | 方法 | 频率 |
|---|---|---|
| 调试 | `ptrace` 状态、`TracerPid`、`/proc/self/status` 一致性 | 启动 + 定时 |
| 注入 | 模块列表与加载时序异常、匿名可执行映射 | 定时 |
| Hook | 关键桩函数字节采样（非全量） | 随机 |
| 环境 | 模拟器/多开/框架特征（**规则包内**，加密+签名） | 启动 + 定时 |
| 一致性 | ART/JNI 关键结构自洽（只读校验，不改写） | 低频 |

### 9.2 响应分级

| 级别 | 触发 | 本地行为 | 服务端 |
|---|---|---|---|
| L0 | 疑似（单点） | 记录 | 观察 |
| L1 | 确认（多点） | 明确可观察的功能降级 | 下发挑战 |
| L2 | 明确攻击 | 受限模式 | 吊销 session / 拒绝签发新 key |

**禁止**：`kill`、`abort`、`_exit` 作为默认响应。

### 9.3 上报

- 事件结构化（`{kind, confidence, evidence_hash, ts}`），本地加密队列，批量上报。
- 不做明文文件队列（对照 §60.4 的本地文件上报）。
- 上报失败不影响主流程。

## 11. 工程化

### 11.1 版本与灰度

| 项 | 策略 |
|---|---|
| 版本三元组 | `shell_version / policy_version / rule_version` |
| 指纹 | APK 内置 fingerprint，服务端判定是否需重新加固 |
| 灰度 | 1% → 10% → 100%，监控崩溃率/启动耗时/留存 |
| 回滚 | 以更高版本签发回滚内容；APK 回滚走发布流程 |

### 11.2 性能预算

| 指标 | 预算 |
|---|---|
| 冷启动增量 | < 150 ms（首帧前） |
| 内存增量 | < 20 MB |
| 首屏 DEX 解密 | < 300 ms（惰性分摊） |
| 后台校验 CPU | < 1%（抽样控制） |

### 11.3 兼容性

| 风险 | 处理 |
|---|---|
| Android 14+ 禁止从可写目录 `dlopen` | Core 从 APK 内加载，不落盘 |

## 12. 安全边界

| 攻击者能力 | 防护 | 残余风险 |
|---|---|---|
| 静态分析 APK/so | 加密容器、签名清单、符号裁剪 | 仍可读到壳结构与公钥 |

| 规则替换 | 加密 + 签名 + 版本门控 | 客户端校验仍可能被绕过 |
| 服务端伪造 | TLS + 双向认证 + attestation | 依赖服务端安全 |

## 16. v1.1 修订：保留透明整包加固的能力目标

本章替代前文冲突的技术限制和验收承诺。目标为无需客户修改业务代码的整包加固；实现难点通过适配层、原型和设备回归解决，不直接削减为 SDK 接入方案。

### 16.1 加载架构

采用公开 API 基线与 ART 适配层两条路线。公开路线使用完整 DEX 缓冲区与 InMemoryDexClassLoader；适配路线按 Android 版本及 ABI 负责类加载器安装、DEX 注册和 Application/组件接管。内部接口通过独立适配器隔离，明确结构布局、调用约定、运行时特征检查、回滚开关与崩溃归因，不再全局禁止。避免默认修改全局 VerifyClass 行为；如确需修改，作为独立实验能力验证其影响。

Application.attachBaseContext 通常先于 provider.onCreate，工厂可能更早调用。加载入口放在经验证的工厂或 attach 阶段；provider 只执行该阶段允许的初始化。业务 provider 创建之前须完成其依赖加载。按进程设计幂等状态机 VERIFIED → KEY_READY → DEX_READY → APP_ATTACHED → RUNNING，失败进入独立恢复流程。恢复入口、资源和组件留在 stub，不依赖加密业务 DEX；构建期生成业务组件门控，密钥到达后受控重启。覆盖原 Application、原 factory、provider、广播、服务、深链和多进程生命周期。

分块加密不等于 ART 按块消费。基线完整认证解密 DEX，按启动依赖分组预加载；页级或方法级恢复单独验证校验器、JIT/AOT、跨页访问与线程并发，不在原型前计入性能收益。ART 使用中的 DEX 映射保持有效，只有不再引用的临时副本才能清零或撤销访问。

### 16.2 密钥模型

每个构建随机生成 256 位 K_content，加密统一容器；安装 ID 只参与授权与设备封装，不改变既有密文的密钥。K_app 留在 HSM，不注入在线档 APK；Ed25519 签名密钥独立管理。设备注册 Keystore 公钥，经服务端验证构建、证书、随机挑战与可用的设备证明后，以经过协议评审的封装方式取得同一构建内容密钥。具体 HSM/Keystore 算法支持及软件降级由原型确认。

提供 online_authorized 与 offline_compatible 两档，均保留透明加载、文件保护及检测。在线档首装联网，可缓存有期限授权；离线档通过隔离的本地材料、构建多样化与运行时组合支持断网首装，但承认静态分析可能恢复密钥，不能计为 G2 达标，也不能使用在线档 K_app。混淆只增加成本。服务端吊销使 session 失效并拒绝新授权，已缓存密钥不能保证即时撤销，必须记录最长离线窗口。设备密钥不可导出不代表进程内内容密钥不可读取。

### 16.3 容器格式修订

基线 AES-256-GCM。每构建随机内容密钥，以 HKDF-SHA-256 按 build_id 和用途标签派生块与 TOC 密钥。块 nonce 为 8 字节随机前缀加 4 字节大端全局块序号，共 12 字节；序号跨所有 DEX 唯一且不得回绕，重新构建不复用密钥/nonce。TOC 独立密钥与 nonce。每块保存 16 字节 tag；AAD 固定编码绑定格式、算法、build_id、文件序号、块序号和明文长度。file_id 截断值仅作标识，不负责 nonce 唯一性。

格式冻结须指定整数端序、字段宽度、长度上限、区域偏移和签名覆盖范围，并拒绝越界、溢出、重叠和未知关键标志。提供跨实现向量以及重排、截断、错误 tag、重复 nonce、超大长度负例。清单覆盖完整容器哈希，避免签名或清单自哈希循环。

### 16.4 透明文件保护

保持无需客户改业务代码的交付目标。原生 I/O 拦截层管理文件句柄和逻辑偏移，构建期 Java 调用点适配补齐 SharedPreferences、流与随机访问。先实现普通文件与 SharedPreferences，再扩展随机访问、映射和数据库；SDK 显式接入仅为优化选项。

覆盖 open/read/write/pread/pwrite/lseek/dup/close、truncate、rename 与锁；独立处理 mmap/msync/munmap、动态库载入、已打开句柄和直接 syscall。不得把 libc 拦截等同全部路径覆盖。未覆盖场景作为待适配项列明；SQLite/WAL 等未通过一致性验证时策略排除，不能宣称已完成功能对等。

文件密钥与 DEX 隔离，分块 AEAD 的 nonce 覆盖重写、随机写和崩溃重试。定义逻辑偏移映射、读改写、稀疏与截断语义、fsync、跨进程锁和原子迁移。规则明确规范化、排除优先、链接和重命名行为。补齐备份、升级、旧格式、卸载重装、密钥丢失与崩溃恢复，禁止不可恢复地覆盖原文件。

### 16.5 证据和安全边界

参照 §39 验证的是 classes.jar 的 14 个 DEX，与动态捕获一致，不能自动推广到 coreclasses.bangcle。§42–44 验证文件算法与真实 XML，但当前包无 RES_RULE，规则可能历史残留。§60 常规 YARA 命中分类并写本地队列；§61 另有终止路径，不能将命中等同杀进程。§45.7 原样本 RSA 清单验证和失败行为仍未知。§62 x86-64 文件位于 arm64 目录仅为观测，其用途未经实机确认，不能直接判为交付缺陷。

每 App 加盐用于隔离配置和产物，不保证共性漏洞无法跨客户利用。规则加密提供有限保密性，签名提供防伪；运行时规则仍可能提取，不能将残余风险写为无。

### 16.6 完整性、更新和兼容

Bootstrapper 内置验证公钥，先验证清单及 Core 完整文件再加载。启动关键产物全量校验，运行时抽样仅提供有限检测。公钥轮换、证书轮换和清单规范化单独定义。客户本地签名前预先提供最终证书，或签名后外部登记，不能签名后修改 APK。回滚通过更高版本签发旧内容；APK 代码回滚走发布流程，离线不能依靠服务端实时防降级。

APK 单包、AAB/split、动态特性、ROM 与 ABI 分开列支持矩阵。16 KB 页同时检查 ZIP 与 ELF LOAD 段及依赖库，zipalign 不能替代 ELF 验证。

### 16.7 原型、排期和验收

M0 增加四项可运行原型：统一容器到多设备授权、透明组件接管与恢复、完整 DEX 加载、透明 SharedPreferences/普通文件保护。各自产出设备矩阵、数据和遗留项后冻结格式与接口。M1 覆盖 S0–S8 最小闭环、运行时、密钥与恢复；M2 扩展文件和规则；M3 推进 ART 适配、检测和吊销。原周期按原型结果更新，不以削减透明目标规避难点。

A1/A2 的静态防护只在在线档、只有 APK 且无授权设备或密钥的模型下验收；工具失败不证明所有攻击失败。A3 同时验证透明 I/O、迁移、并发和崩溃恢复。A4 分开验证保密与签名。A5 区分全量校验与抽样；断网仅尽力上报。A6 在线档进入恢复界面，离线档正常启动。A9 分开记录 session 吊销、新授权拒绝及缓存最长有效窗口。

150 ms 为本地已有密钥路径的待验证目标，首装网络延迟单列。按设备、ABI、DEX 规模、冷暖缓存和网络分别报告首帧、业务可用、解密加载、峰值 RSS 的 P50/P95/P99 及样本量；20 MB 内存目标按包规模重新定档。灰度定义百分点、对照组、最低样本量和置信区间，1% × 72 小时本身不充分。

### 18.5 首轮集成、C ABI 与编译加固

首轮建议组合保持 Java stub + C++17/NDK Core + Python 编排 + dexlib2 工具 + 官方打包工具；ByteHook 为 PLT 首选原型，ShadowHook 补必要入口；BoringSSL/cryptography 负责密码，YARA 执行规则，Go/PostgreSQL 服务端。候选状态不因写入本组合自动变为 selected。

**C ABI 是 Bootstrapper/Core/适配器的对外二进制边界，C++17 仅在 Core 及实现模块内部使用。** 与 §10.1 对齐：使用 extern C、固定宽度整数、不透明句柄、明确错误码和释放函数，增加 abi_version/struct_size；不跨边界传 STL、异常、RTTI 或不同 allocator 的内存。JNI 以 JNI 类型和显式所有权衔接；Java 异常转换与 C++ 异常不得任意穿越边界。Python/Java 工具协议独立版本化。

编译基线评估 -fstack-protector-strong、按 NDK/bionic 支持的 _FORTIFY_SOURCE、-Wl,-z,relro 与 -Wl,-z,now、隐藏内部符号、优化和可选 LTO；PAC/BTI 仅在相应架构、工具链和系统组合验证后启用。不得笼统加到所有 ABI。strip 发布包但保留私有符号与 Build ID，用于 §17 OPS-02 归因。检查产物中实际 canary、RELRO/NOW、导出表、ELF/ZIP 对齐，不以命令参数存在代替验证；LTO/CFI/Hook 相互作用和各配置性能分别回归。

### 18.6 供应链、版本维护与退出条件

引入时生成 components.lock：OSS ID、仓库、完整 commit、tag、源码/发行包 SHA-256、依赖锁、license_expression、NOTICE/源码义务、scope、具名 owner、ADR 与报告位置。Gradle/Python/Go/native 构建依赖均纳入，禁止只锁顶层版本；产物签名及校验和保留，固定依赖获取来源。

每次发布由 Syft 或相应生态工具生成 SBOM，输出 CycloneDX 格式（可另存 SPDX）；结合 Gradle/Python/Go/native 构建记录补齐静态链接及 vendored 库，不能仅靠 APK 扫描发现所有组件。OSV-Scanner/Trivy 按适用生态扫描，记录数据库版本和时间；无 CVE 命中不等于无风险。ScanCode 辅助识别许可，人工确认多许可选择、传递依赖、NOTICE 与源码义务。生成客户端第三方声明、内部构建工具清单、服务端清单三份交付视图。

供应链负责人按周关注漏洞与上游安全公告，安全公告触发即时评估；按月检查升级候选。组件 owner 对升级、移植、兼容和回滚负责：BoringSSL 不承诺稳定 API；YARA 内部 arena/编译规则需随版本重建；Hook 后端的 ABI/16 KB/BTI/PAC 支持随版本变化。可达的高危/严重漏洞或许可冲突默认阻断发布，例外需具名审批、补偿措施、截止日期及跟踪项；扫描误报保留证据与复查期限。

进入 selected 前：固定提交、许可审核、依赖锁、ADR 和负责人齐全。进入 verified 前完成：

1. DEX/AXML 保真与重打包验证，包括 debug info、hidden API 元数据、特殊 DEX 格式、资源 ID 和未知属性。
2. Hook 并发/递归/动态模块/卸载及目标 ABI、ROM、16 KB 和架构保护测试，直接 syscall 未覆盖显式记录。
3. 密码三端向量、认证失败、截断、nonce、版本测试；YARA 九规则及缺一特征、字面量变化、超时用例。
4. 设备侧生命周期、SharedPreferences、I/O 故障恢复和错误归因；云设备场仅补充矩阵。
5. SBOM、许可证和漏洞扫描、产物编译加固检查与私有符号留存通过，第三方声明齐全。
6. clang-tidy 等静态分析及可复现检查：固定源码/工具链/配置比较；diffoscope 区分时间戳、签名、随机密钥和构建盐的预期差异。真实发布保持安全随机，不能为字节相同而复用密钥/nonce；测试重放随机输入仅限隔离测试，禁止进入生产。

升级后重新 verified，状态记录保留测试范围和时间。已有包无法回滚的组件必须提前准备修复发布方案。

| 候选 | 当前决定与原因 | 重新评估条件 |
|---|---|---|
| xHook | 暂不选；PLT 层先集中验证 ByteHook，减少同类维护面 | 主方案出现明确平台/行为缺口时对照原型并核许可 |
| SandHook / Pine | 暂不选；Java/ART 方法 Hook 不是当前整个加载与组件接管方案的替代 | 明确需要方法 Hook 且现有 ART 适配无法满足时比较；独立核验许可 |
| OpenSSL | 暂不作为客户端首选；已有 BoringSSL 评估路线，避免维护两套密码后端；不预设体积结论 | BoringSSL API 维护或目标能力不适合时比较固定版本、体积和支持周期 |
| mbedTLS | 保留密码替代候选；AES-GCM/HKDF/Ed25519 的完整支持、配置及许可须按版本实证 | 原型证明所需算法、维护与体积更适合时替换，不按项目名猜算法支持 |
| YARA-X | 暂不选主线；现有九规则和 C/C++ 测试链先用 YARA，避免同时变更引擎和集成工具链 | 对照规则语义、C API、Android/Rust 构建、超时和资源行为后可替换，不要求兼容旧私有 arena |
| 自定义 ELF linker / LLVM 混淆 fork | 延后；先完成透明主链路，单独维护成本高 | 明确保护收益且有专项兼容验证时增加，不取消长期能力目标 |

每个重新评估通过 ADR 更新版本、状态、功能关联和 fallback；未核验许可证及未固定提交的候选不得直接变成生产依赖。


## 19. 前后端与 Android 平台架构

采用 [架构选型.md](架构选型.md)：Vue 3/TypeScript/Vite/Element Plus，Go/Gin 单体 API，PostgreSQL/pgx，Python 独立 worker 与流水线，Java/dexlib2 工具，Java/C++17 Android app + shield。Go 管业务和任务，Python 管 APK，Android 管运行时。任务表作为初期队列、SSE 展示进度、产物先本地存储。仅四个顶层目录，不提前拆微服务；机制通过描述、构建步骤、运行时能力和测试扩展。具体边界及阶段依架构选型与实施步骤。
